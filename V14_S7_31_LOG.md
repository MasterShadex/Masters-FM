## S0.4 MECHANISM -- full flow

TYPE: custom auto-updater (NOT Squirrel/WiX-auto). Engine lives ENTIRELY in the WPF tray
(`src/tray_csharp/Update/UpdateCheckService.cs`), a 7-state machine
(Idle->Checking->Available->Downloading->Ready->Installing,+Error). server.js is RETIRED legacy
(not in the live path). launcher.cs is update-agnostic (process host only). The installed tray
is MastersFM_Tray.exe (= dist WPF MastersFM_Tray_v14.exe).

PUBLISH half (operator -- the only GitHub-touching path):
  1. bump version in version.json; run `_full_rebuild.ps1`:
     - [2b/5] signs the MSI via _sign_msi.ps1 with a SELF-SIGNED cert `CN=MasterShadex, O=MasterShadex`
       (FriendlyName "Master's FM Code Signing", CurrentUser\My, 5y, signtool /fd SHA256 timestamped).
     - [2c/5] stamps version.json = { version, msi_url = github releases/download/v<ver>/Masters-FM-V<ver>.msi,
       msi_sha256 = SHA256 of the SIGNED msi, autoInstall=false }.
  2. operator MANUALLY creates a GitHub Release tagged v<ver> + uploads the MSI (web UI step).
  3. operator runs `_push_update.ps1`: flips autoInstall=true (unless -NoAutoInstall) ->
     `git add version.json` -> `git commit -m "release v<ver>"` -> **git push origin main**.
     <-- THIS is the live-remote action. It is the ONLY script doing `git push`. NEVER run it this stage.

CLIENT half (friend -- WPF tray):
  - CHECKS-WHERE: GET https://raw.githubusercontent.com/MasterShadex/Masters-FM/main/version.json?t=<ms>
    (cache-busted) on a 6-hour startup cadence + on-demand ("Check for Updates").
  - COMPARES-WHAT: SemVerComparer.Compare(remoteVersion, localVersion). localVersion =
    the tray assembly's AssemblyInformationalVersion (NOT version.json on disk). Pre-release
    (rc/beta/alpha) REJECTED by policy. Only transitions to Available when remote > local (cmp>0).
  - DOWNLOADS-FROM-WHERE: manifest msi_url (GitHub Releases) -> streamed to
    %LOCALAPPDATA%\MastersFM\downloads\MastersFM_update_v<ver>.msi.partial (progress events).
  - APPLIES-HOW: 3-gate verify then install:
      (1) SHA256(download) == manifest msi_sha256 ;
      (2) Authenticode: X509Certificate.CreateFromSignedFile -> chain.Build(cert) MUST succeed
          (RevocationMode=NoCheck) AND subject must contain `CN=MasterShadex` ;
      (3) atomic File.Move(.partial -> final).
    Then msiexec.exe /i <final> /quiet /norestart (ProcessStartInfo+ArgumentList, no shell) ->
    Application.Current.Shutdown(0) so the MSI can replace files. autoInstall=true auto-chains
    Download->Install; false = user clicks Install in the WPF UpdateProgressWindow.
  - ON-FAILURE-WHAT: every failure deletes the .partial and reverts to Available/Idle (no install):
    network/404 (EnsureSuccessStatusCode throws), JSON parse fail (-> Idle "no update"), missing
    version (-> Idle), SHA mismatch (-> delete+Available), Authenticode fail (-> delete+Available),
    cancel (-> delete+Available). The `.partial` is never promoted to `final` unless BOTH (1)+(2) pass.

version.json ROLE = DUAL: (a) on repo `main` (raw.githubusercontent) it is the UPDATE MANIFEST the
client polls; (b) locally it is build metadata stamped by _full_rebuild.ps1 + served by GET /version
for the overlay/PWA -- it is NOT the source of the updater's "local version" (that's the assembly attr).
Shipping/dev version.json stays 14.0.0.

UI surfaces (non-authoritative): server_dotnet serves GET /update (update.html) + GET /update-status
+ GET /version. These are status/progress display only; the safety logic is all in UpdateCheckService.

AUTO vs MANUAL: AUTO-UPDATE EXISTS (Phase B applies). First-time install is manual MSI; thereafter
the tray self-updates per the flow above.

BLAST RADIUS: a push to `main` reaches EVERY friend with the app installed, within ~6h (or on next
"Check for Updates"). A single bad push affects all of them.

## S0.5 RISK assessment
| Risk | State | Notes |
|---|---|---|
| malformed manifest -> crash | SAFE (absent) | JSON parse catch -> Idle ("no update"); never crashes the tray |
| 404 / network fail | SAFE | EnsureSuccessStatusCode throws -> caught -> delete partial -> Available |
| partial / truncated download | SAFE | SHA mismatch -> delete + Available; .partial never promoted |
| hash verification | PRESENT | SHA256(download) vs manifest msi_sha256, ordinal lowercase compare |
| signature verification | PRESENT | Authenticode chain.Build + CN=MasterShadex exact match |
| downgrade protection | PRESENT | only cmp>0 -> Available; pre-release rejected; unparseable -> no update |
| failed-install rollback | PARTIAL | Windows Installer rolls back a FAILED msiexec txn; NO app-level revert of a SUCCESSFUL-but-broken build |
| **self-signed chain trust** | **UNKNOWN / LIKELY-BLOCKING** | VerifyAuthenticode REQUIRES chain.Build to succeed. A self-signed cert NOT in the machine's Trusted Root yields UntrustedRoot -> Build=false -> update REJECTED. On friends' machines (and possibly the operator's, if the cert was never added to Root) this could reject EVERY legit MSI. The disabled bootstrapper was the thing that did cert-store install. THIS is the #1 dry-run probe. |

NET: the updater is robust against transport/corruption/tampering (good design -- 3 gates + safe
failure). The two real risks are (a) a validly-signed-but-functionally-broken build (no auto-revert),
and (b) the self-signed-chain-trust question that could block updates entirely. Both are exactly what
a dry-run must answer before any real release.

## S0.6 Phase B recommendation (dry-run design -- for operator approval)
Auto-update EXISTS, so Phase B is warranted. Recommended approach -- NO protected edits, NO real
GitHub, NO version bump, dry-run source fully local:

  PROBE 1 (highest value, cheapest): replicate VerifyAuthenticode's exact logic
  (X509Certificate.CreateFromSignedFile -> chain.Build -> CN check) in a throwaway script and run it
  against the ACTUAL current signed install MSI, on this machine, with the cert NOT trusted in Root --
  answers "would a friend's tray accept our signed MSI?" If it FAILS, the update path is blocked
  as-is and 7.31.1 hardening is required BEFORE any release.

  PROBE 2 (decision logic): drive UpdateCheckService.ProcessManifestJson (it is `internal` + was
  explicitly factored "so tests can drive synthetic payloads without real HTTP") with synthetic
  manifests: good-newer -> Available; malformed -> Idle; missing-version -> Idle; pre-release -> Idle;
  equal/downgrade -> Idle. Needs InternalsVisibleTo OR a throwaway test csproj referencing the Update
  classes (a NON-protected build-file question -- flag at gate). Alternative: standalone re-implementation
  (tests a COPY of the logic, not the shipped binary) if referencing proves invasive.

  PROBE 3 (download/verify): run DownloadAsync against a LOCALHOST http server (or file source)
  serving (a) a COPY of the real signed MSI w/ correct SHA -> Ready; (b) truncated -> SHA fail ->
  Available; (c) 404 -> Available; (d) wrong-cert/unsigned -> Authenticode fail -> Available. Proves
  good-applies + bad-fails-safe.

  NOT in the dry-run without explicit gate approval: actually running msiexec /i on any artifact
  (could modify the real install). Stop at "Ready"; a controlled MSI-over-MSI install test only if
  the operator approves it at the gate.

  REDIRECT NOTE: editing UpdateCheckService's `const ManifestUrl` to localhost = "changing updater
  behavior" (OUT OF SCOPE -> 7.31.1) -> do NOT. The test-seam + local-source approach above avoids it.
