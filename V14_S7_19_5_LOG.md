## S0.5 Choose fix shape (initial lean, locked in S1.4)

### Option recap (with codebase-specific evaluation)

**Option A -- make `SelectedDevice` settable:**
- Add `set => SelectDevice(value);` (or null-safe variant) to `SelectedDevice` property
- XAML stays TwoWay
- Smallest diff: ~2 lines in 1 file (AudioDeviceViewModel.cs)
- Restores BOTH the exception-free bootstrap AND functional user-click-persists-device behavior
- **Risk:** violates the file-header design comment ("User clicks forwarded via SelectDevice(); programmatic changes via SetSelectedDeviceSilent()" -- adding a property-setter write-path is a third route). But: grep verification (S0.4.3) shows only ONE TwoWay binding exists, and routing through `SelectDevice()` in the setter preserves the persist-on-user-click semantics that path already enforces.

**Option B -- change wizard XAML binding to `Mode=OneWay`:**
- XAML edit: single attribute change (TwoWay -> OneWay)
- AudioDeviceViewModel.cs unchanged (preserves the read-only contract)
- Smallest diff: ~1 line in 1 file (SetupWizardWindow.xaml)
- Eliminates the exception
- **Risk:** with OneWay, the user's click does NOT propagate back to AudioVm.SelectedDevice -- the wizard's audio-source selection becomes dead. The Audio step's `<ListBox SelectedItem={Binding ... OneWay}>` shows the VM's current selection but discards user clicks. The wizard becomes a display-only audio step. ((PARTIAL FIX -- eliminates exception but leaves wizard partially non-functional.))

**Option C -- retarget the binding to a writable property:**
- No existing writable property to target. The VM exposes only computed read-only properties (`SelectedWasapiDevice`, `SelectedMmeDevice`, `SelectedKsDevice`, `SelectedAsioDevice`, all `=> _selectedDevice?.Backend == "..." ? _selectedDevice : null`) and the `OutputDevices` ObservableCollection.
- A pure Option C would require adding a new writable property (`SelectedDeviceId` or similar) just for the wizard binding -- larger diff and more violations of the read-only design than Option A.
- **Risk:** larger diff for no functional gain over A.

**Option C-prime -- event-driven (matches `AudioDeviceWindow.xaml` pattern):**
- XAML: remove `SelectedItem="{Binding SelectedDevice, Mode=TwoWay}"`, add `SelectionChanged="OnDeviceSelectionChanged"` on the ListBox
- XAML: add `<Setter Property="IsSelected" Value="{Binding IsActive, Mode=TwoWay}"/>` to `WizardDeviceItemStyle` so visual selection tracks `IsActive` (matches `DeviceListItemStyle` line 126)
- Code-behind: add `OnDeviceSelectionChanged` handler that calls `((AudioDeviceViewModel)((ListBox)sender).DataContext).SelectDevice(device)`
- 3-4 changes across 2 files
- Matches the architectural pattern that Stage 7.12 Batch A rev14 explicitly defined for `AudioDeviceWindow`
- Smallest fully-correct diff
- **Risk:** larger diff than Option A; depends on `IsActive` flag mutation propagating correctly (which it does in AudioDeviceWindow -- the `NotifySelectionChanged()` method on line 138-153 iterates all device collections and updates `IsActive`).

### Initial lean: **Option A**

Rationale:
- Smallest possible diff that fully fixes both observable failures (exception + dead-click)
- Grep verification shows only ONE caller of the writable binding (the wizard) -- so adding a setter doesn't open up risk surface elsewhere
- Routing the setter through `SelectDevice()` preserves the persist-on-user-click semantics
- The design comment's concern ("programmatic changes via SetSelectedDeviceSilent") is honored because the new setter targets the USER-CLICK path (`SelectDevice`), not the programmatic-silent path -- WPF TwoWay bindings DO represent user-driven writes
- INotifyPropertyChanged: already fires via `SelectDevice -> NotifySelectionChanged -> OnPropertyChanged(nameof(SelectedDevice))` -- no extra plumbing needed

**Provisional code shape (subject to S1.4 lock):**

```csharp
public AudioDeviceInfo? SelectedDevice
{
    get => _selectedDevice;
    set
    {
        // WPF TwoWay binding write-path. Routes through SelectDevice (the
        // user-click semantics) when a real device is provided; null is
        // routed through SetSelectedDeviceSilent (no persistence) since
        // SelectDevice signature is non-nullable. Stage 7.12 Batch A rev14
        // design comment honored: the setter does NOT introduce a new
        // mutation path -- it forwards to the existing ones.
        if (value != null) SelectDevice(value);
        else               SetSelectedDeviceSilent(null);
    }
}
```

## S1.3 Identify the write-path

**Critical finding:** The wizard never reads `AudioVm.SelectedDevice` after the user clicks.

`SetupWizardViewModel.NextAsync()` (lines 72-111) on the `WizardStep.Audio` case (line 84-89) ONLY advances state -- it does NOT read `AudioVm.SelectedDevice` to act on the user's selection:

```csharp
case WizardStep.Audio:
    CurrentStep = WizardStep.Platforms;
    UpdateStepUi();
    PlatformsVm.RefreshFromConfig();
    await Task.CompletedTask;
    break;
```

This means the wizard relies on the **click itself** to persist the device choice -- via the TwoWay binding's write-back → setter → persistence chain.

`AudioDeviceViewModel.SelectDevice(AudioDeviceInfo device)` (lines 122-128) is the user-click write-path:
- Skips if device unchanged (re-entry guard)
- Updates `_selectedDevice`
- Calls `NotifySelectionChanged()` (which iterates all device collections setting `IsActive` flags AND fires `OnPropertyChanged(nameof(SelectedDevice))`)
- Calls `ApplyDevice(device)` (which persists to config + posts to server)

`AudioDeviceViewModel.SetSelectedDeviceSilent(AudioDeviceInfo?)` (lines 132-136) is the programmatic write-path:
- Updates `_selectedDevice`
- Calls `NotifySelectionChanged()` (visual update only, no persist)

**Answer to the brief's three S1.3 questions:**

1. ❓ Does the wizard write the user's device choice back through the SelectedDevice binding (requires TwoWay → Option A)?

   **YES.** The only path that persists the user's click is the TwoWay binding's write-back chain. With Mode=OneWay, the click would be visually accepted (WPF tracks selection internally) but `_selectedDevice` would never update + nothing would persist + the wizard's audio step would be fully dead. Option A required.

2. ❓ Or does the wizard call a method like `SetDevice(deviceId)` and the binding is just for display (allows OneWay → Option B)?

   **NO.** No code path in `SetupWizardWindow.xaml.cs` nor `SetupWizardViewModel.cs` calls `SelectDevice()` or `SetSelectedDeviceSilent()` directly. The wizard exists purely as a thin XAML-driven UI over `AudioDeviceViewModel`; the user-click event → TwoWay binding → property setter → SelectDevice() chain is the wizard's entire device-selection mechanism.

3. ❓ Or is the binding actually targeting the wrong property entirely (suggests Option C)?

   **NO.** The binding correctly targets `AudioDeviceViewModel.SelectedDevice` which IS the property that represents the currently-selected device. There is no other writable property that the binding could target; all other VM properties are read-only computed views (`SelectedWasapiDevice` etc.) or collections (`OutputDevices` etc.).

## S1.4 Lock fix shape: Option A

**Final choice: Option A -- add a public setter to `SelectedDevice` that routes through the existing `SelectDevice()` and `SetSelectedDeviceSilent()` methods.**

### Why Option A and not B or C

| Aspect | Option A | Option B (OneWay) | Option C (retarget) | Option C-prime (event-driven) |
|---|---|---|---|---|
| Eliminates exception | YES | YES | YES | YES |

**Trade-off accepted:** Option A introduces a third write-path (the setter), which the design comment cautioned against. But:
- The setter forwards to the EXISTING `SelectDevice()` user-click path -- it does NOT introduce a new mutation behavior, only a new WPF entry-point into the same path
